Case study 03 · Systems & process

Training for a tooling overhaul

A complete change of content tooling, with the work itself staying the same

The team moved to entirely different content software. The work barely changed — draft, review, publish, same people, same standards — but the interface was unrecognizable. The training's job was to get people fluent in a new UX, fast.

My role

Designer and writer — analysis, curriculum, process documentation

Audience

Writers, SMEs and reviewers moving to the new software

Format

Workflow-based ILT, walkthrough guides, live process reference

Constraint

New tool still being configured while training was being written

The problem

The natural fear in a tooling migration is that everything is new. It wasn't. The process held: same stages, same owners, same quality bar. What changed was the software underneath it.

Teaching it as a feature tour would have missed that and had a shelf life of about a sprint. Plus, the new tool configuration was still moving, so anything built on screenshots would be wrong before launch.

What analysis found

  • 01

    Mapping old against new showed how much carried over. Naming that up front took the temperature down — people stopped bracing for a new job and started learning a new tool.

  • 02

    The friction was in the small stuff: where drafts live, how review comments arrive, what publishing feels like now. Individually trivial, collectively the reason people stall.

  • 03

    The old tooling was hardest on the people with the least practice in it — SMEs, who used it occasionally and paid for that every time. The new tool changed the published experience too, so readers were meeting a new UX at the same time authors were.

What I built

Foundation

The process, written down

One page: stages, owners, entry and exit criteria — tool-independent on purpose. It became the reference the training pointed at, and it outlived the migration.

Core

Workflow-first sessions

Each session followed one real document from draft to publish, in the new software. Steps appeared where they occur in the work, so the new tool got learned in the shape of the job people already knew.

Durability

Guides built to be updated

Short task guides structured so a configuration change means editing one step — not re-recording a video. Necessary when the tool is still being set up around you.

Results

Kirkpatrick levels 1–4

LevelWhat was measuredWhat happened
L1 · ReactionSession feedbackWriters and SMEs both said the workflow framing answered the question they came in with: what am I now responsible for. Feedback was positive across both groups, though not formally scored.
L2 · LearningWalkthrough completionParticipants moved a real document end to end during the session, including the review handoff.
L3 · BehaviorProcess adherenceReview handoffs moved cleanly into the new tool rather than lingering in the old one — no parallel workflow running on the side.
L4 · ResultsTime to publishRelease notes shipped two days faster, and no migration-quarter stall. −2 days

Marked items are numbers to fill from system reports; the rest are observed outcomes I can speak to directly.

What I'd do differently

I'd open with a sandbox week. People absorbed the "your job is the same" message quickly; confidence in the new software came only from unsupervised time in it, and that should have come before the sessions, not after.

I'd also name a process owner on day one. I wrote the process document; someone needed to own keeping it true as the tool got reconfigured.
